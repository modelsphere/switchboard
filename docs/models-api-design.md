# switchboard: `/v1/models` filtered by caller key

Status: draft · Tracking: modelsphere/higress#5 (roadmap 2.3)

## Goal

`GET /v1/models` and `GET /v1/models/{id}` return only the models the calling
API key is allowed to use. The list is **derived from the gateway's own
config**, so it cannot drift from what Higress actually enforces.

Non-goals: enforcement (it stays in Higress: model-router + per-model routes +
key_auth `allow`), model-mapper aliases, Anthropic-format listing, admin UI.

## Request path

```
client ─▶ Higress ─ key_auth (sets X-Mse-Consumer, strips client copy) ─▶ switchboard
```

- Higress routes `/v1/models` and `/v1/models/*` to the switchboard Service.
  key_auth **must** be active on that route (`global_auth: true`, or a
  `matchRules` entry for it); otherwise `X-Mse-Consumer` can be forged.
- switchboard Service is ClusterIP; a NetworkPolicy admits only gateway pods.
- Missing/empty `X-Mse-Consumer` → `401` (OpenAI error shape).

## Source of truth

The Higress console is not used. Per-model routes and key_auth are plain
Kubernetes objects (hand-written now, generated by switchboard later), written
in the same shape the console's AI routes produce, so the conventions stay
familiar. switchboard reads them with read-only RBAC through informers, so
changes take effect without a restart:

| Object | What switchboard takes from it |
|---|---|
| `networking.k8s.io/v1 Ingress` (gateway's ingress class) | routes matching the model header: `higress.io/exact-match-header-<model-header>: <model>` → route `ns/name` serves `<model>` |
| `extensions.higress.io/v1alpha1 WasmPlugin` key-auth | `defaultConfig.global_auth`, `matchRules[].ingress` + `config.allow` |

`<model-header>` is configurable (default `x-higress-llm-model`, matching the
model-router `modelToHeader`). Only the `higress.io/` annotation prefix
counts; Higress ignores the nginx prefix for header matches. Route names
follow Higress: `name` for Ingresses in the system namespace, `ns/name`
otherwise. That is the string `matchRules[].ingress` must use. The
key-auth WasmPlugin is selected with `--key-auth-plugin ns/name`, or found
by its `url` in the system namespace when exactly one matches.

The catalog sits behind a `Source` interface, so a DB source can replace it
once switchboard owns keys, without changing the endpoint.

### Derivation rules

switchboard reproduces two stages of Higress:

1. **Controller** (`pkg/ingress/config/ingress_config.go`
   `convertIstioWasmPlugin`): the WasmPlugin CR becomes the plugin's JSON.
   `spec.pluginConfig`, when set, is used verbatim, and `defaultConfig` and
   `matchRules` are then ignored. Rules with `configDisable: true` are
   dropped. With `defaultConfigDisable: true` and no rules left, no plugin is
   applied.
2. **Plugin** (`plugins/wasm-cpp/common/route_rule_matcher.h`
   `parseAuthRuleConfig`, key_auth `parsePluginConfig`): the same accept or
   reject decisions, including consumer validation (name, exactly one of
   `credential`/`credentials`, no duplicate credential, `keys`,
   `in_query`/`in_header`). An instance config the plugin cannot parse is
   ignored when rules exist; without rules the plugin rejects the whole
   config.

Matching then mirrors `getMatchAuthConfig`, `checkAuthRule` and key_auth
`checkAllowSet`. For each model route R serving model M, with the request
host H taken from the `/v1/models` request:

1. R is skipped when its Ingress hosts do not cover H. Wildcard hosts follow
   Envoy, which the gateway runs: `*.x.com` is a suffix match, so it covers
   `a.b.x.com` too.
2. The **first** matching rule, in `matchRules` order, decides. The rule's
   category follows the plugin: `ingress` (route name) first, then
   `_match_route_prefix_` (from a verbatim `pluginConfig` only), then
   `service`, then `domain`. A lower category on the same rule is ignored.
   `domain` matches H (`*.x` suffix, `x*` prefix, otherwise exact). Rules
   with `service` are never treated as matching, and a warning is logged.

| Matched rule / instance config | Consumers allowed on M via R |
|---|---|
| rule `allow: [a, b]` | `{a, b}` ∩ configured consumers |
| rule `allow: []`, **or rule without `allow`** | nobody (key_auth uses the rule's empty allow set) |
| rule with its own `consumers` | those consumers; `allow` is ignored |
| rule with `config: {_disable_: true}` | nobody listed (route open) |
| no rule matches, `global_auth: true` | every configured consumer |
| no rule matches, `global_auth` unset/false | nobody listed (route open) |
| no rules at all, `global_auth` unset | every configured consumer |
| no rules at all, `global_auth: false` | nobody listed (route open) |
| config key_auth would reject, or no or several key-auth plugins | nobody |

"Route open" means key_auth does not authenticate R. Such a model is listed
for nobody, and switchboard logs each open model route as a
misconfiguration. A model served by several routes is listed when any of them
allows the consumer, with `created` taken from the earliest such route.
Prefix/regex model matches (`prefix-match-header-…`, `regex-match-header-…`)
cannot be enumerated: they are skipped and logged.

## API

OpenAI shape only.

- `GET /v1/models` → `{"object":"list","data":[{"id","object":"model","created","owned_by"}]}`,
  sorted by id. `created` = route creation timestamp (earliest across routes);
  `owned_by` = `"modelsphere"`.
- `GET /v1/models/{id}` → the single object, or `404 model_not_found` when the
  model is not served **or** not allowed (no existence probing).
- `/healthz`, `/readyz` (ready after first informer sync).

## Verification plan

Unit tests (`go test ./...`) cover every row above. They also cover rule
order, domain vs. route rules, Ingress hosts and wildcards, union across
routes, the system-namespace route name, ingress class (Higress's
annotation-first and `nginx` rules), the annotation prefix, and the
controller and plugin accept/reject cases. Each mirrored decision was checked
by reverting it and seeing a test fail. On the API side: 401 without the header, 404 for disallowed
and for missing models (same body), model ids containing `/`, 503 before
the first sync.

kind + real Higress controller: two keys see different lists; each listed model
is callable with that key and each unlisted one is rejected by the gateway; an
`allow` edit shows up without restart. It also confirms three gateway
behaviours the derivation relies on but unit tests cannot show:

- key_auth evaluates the per-model route model-router re-selects.
- The client's `Host` reaches switchboard unchanged.
- A `*.x.com` Ingress host also serves `a.b.x.com`.
